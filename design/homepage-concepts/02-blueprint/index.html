Resolver · specification

A pure function between Git and your agents.

Given your sources and config, the resolver returns the same result every time. When two sources ship a skill with the same name, source priority decides — the lower number wins. The losers stay visible: dalo status reports them as shadowed.

Input
Active sources + config
Output
One resolved set, linked into every enabled target
Rule
Same name: the lowest priority number wins
Losers
Reported as shadowed, conflicts stay visible
Re-run
Byte-for-byte identical on the same inputs

General notes

Unless otherwise specified
Core rule

Dalo may manage what it owns. It does not take ownership by surprise.

  1. Never overwrites unmanaged files or real folders. A path Dalo didn't create is reported as a conflict, not replaced.
  2. Removes only links it owns. Unlinking a target cleans up Dalo's symlinks and nothing else.
  3. Dirty team checkouts block refresh instead of losing your edits.
  4. Catalog skills need explicit selection and approval before they reach an agent folder.
  5. --dry-run everywhere. Prints the plan, writes nothing.
  6. Conflicts stay visible in dalo status until you resolve them.
  7. Every blocking state names the next command. Typos get a did-you-mean; dalo doctor turns health into findings with a fix each.
  8. Instruction packs write only managed blocks inside agent instruction files. Everything outside the markers stays yours.
  9. Autosync never grants approvals. The launchd or systemd user timer applies existing ones and fails closed.
  10. Plugin tools and hooks are approved separately, by the SHA-256 of their exact contract. Change one field and the approval is gone.

Tolerances

Dalo mutates files on your machine, so its limits are stated like a machinist's: a nominal value and how far it may deviate.

No.CharacteristicNominalTol.Control
01Unmanaged files or real folders overwritten0±0Ownership check before every write; conflicts reported, never forced
02Links removed that Dalo didn't create0±0Removes only links it owns
03Deterministic preflight rules per active skill15localRun before a link is created
04High / critical findings passed without sign-off0±0Blocked until an explicit, content-bound risk acceptance
05Findings cleared by the optional agent reviewer0±0Sandboxed Codex, Claude or OpenCode CLI can add findings, never clear one
06Team catalog versionexact commitno driftPinned in dalo.toml via dalo team catalog add
07Resolver re-run on identical inputsidenticalbyte-for-bytePure function, no hidden state
08Approvals granted by autosync0±0Scheduled runs apply existing approvals only
09Local edits lost to a team refresh0±0Dirty checkouts block the refresh
10Migration commands for stores from 0.6.0+0±0Opens as-is, no re-approval

Note: a passing preflight is not a safety guarantee. It is a deterministic floor; read the evidence with dalo audit before you approve.

Assembly sequence

Main assembly · steps 1–6
  1. 1Create the store

    Sets up ~/.dalo.

    dalo init
  2. 2Find your agents

    Reports which agent folders exist.

    dalo target detect
  3. 3Link targets

    Record where skills should land.

    dalo target link codex
dalo target link claude
  4. 4Add the team source

    Any Git repo of skills.

    dalo source add company git@github.com:acme/agent-skills.git
  5. 5Sync

    Resolve, check, link. Safe to re-run.

    dalo sync
  6. 6Inspect

    Conflicts and pending approvals stay visible.

    dalo status
