Lead story  ·  Team tooling

Your team's agent skills, versioned like code.

Dalo keeps your team's agent skills in Git: one approved set, resolved the same way on every machine and reviewed before it reaches any agent folder.

By Sebastian SoftwareFiled from ~/.daloFor Claude Code, Codex & co.

Agent skills are becoming op­er­a­tional knowl­edge. They en­code how a team works: how it reviews an incident, how it writes release notes, how it ships. Yet most of them still live in one machine's folder, a pasted snippet or a chat thread. Over time the versions di­verge, own­er­ship blurs, and the same skill behaves differently for everyone.

Dalo treats that knowledge the way engi­neers already treat code. Skills live in Git: in a private local source, in team repos­i­to­ries, or in public catalogs you select from one skill at a time. Dalo checks them out into its own store at ~/.dalo, which keeps sources, locks, trust and audits. The store is the source of truth; the agent folder is an output, not the database.

From the store, a resolver computes one active set. It is a pure function: the same inputs give a byte-for-byte iden­ti­cal result on every machine. When two sources ship a skill with the same name, priority decides, lower number wins, and the loser is reported as shad­owed rather than si­lently dropped.

Before anything reaches an agent, a security preflight runs 15 de­ter­min­is­tic rules locally.1 High and critical findings block the sync until someone records an explicit, content-bound risk ac­cep­tance, and catalog skills wait for dalo approve skill.

Only then does Dalo link the result, as direc­tory sym­links, into the folders your agents already read. It never overwrites a file or folder it did not make, removes only the links it owns, and blocks a refresh rather than lose an un­com­mit­ted edit in a team check­out.

There is no daemon and no service to run. Dalo is a single Rust binary for macOS and Linux that shells out to the git already on your PATH.

A3  ·  Resolver, safety, review

Resolver

Priority, not luck.

Same name, one slot, and a verdict you can read.

The resolver is a pure function. Give it your sources and con­fig and it re­turns the same result every time; re-running it on the same inputs is byte-for-byte identical. Source priority decides same-name conflicts, and the lower number wins.

SourcePrioSkill review
local0linked
company10shadowed
oss20shadowed

Losers are not deleted or hidden. They stay visible in dalo status.

Safety

A sync that never overwrites.

Dalo writes only the paths it owns.

  • Never overwrites unmanaged files or real folders.
  • Removes only the symlinks it created.
  • A dirty team checkout blocks the refresh instead of losing your edits.
  • Catalog skills need explicit selection and approval.
  • --dry-run everywhere: print the plan, write nothing.
  • Conflicts stay visible in status, never forced.

Review desk

Nothing ships unread.

A local preflight, then your explicit approval.

Fifteen de­ter­min­is­tic rules run locally over every active skill before a link is created.1 High and critical findings block the sync until someone records an explicit risk ac­cep­tance, bound to that exact content.

An optional agent re­viewer, run sand­boxed through the Codex, Claude or OpenCode CLI, can add findings. It can never clear one. Ap­provals are source-qualified and stay in your own store; read the evidence first with dalo audit.

A5  ·  Opinion

“An installer already does this.”

Every catalog ships a one-off install command. It copies the skill into my agent's folder. Why would I want another CLI?

A reader who installs things once

The editor repliesA one-off installer copies a skill once. Nothing pins the commit, nothing reaches your teammate's machine, nothing notices when upstream changes. Dalo pins the exact commit, records approval and resolves the same set everywhere. Find a skill on skills.sh, then let Dalo pin and deliver it.

“My dotfile repo is enough.”

I keep my skills in my dotfiles and symlink them myself. Done.

A reader with very tidy dotfiles

The editor repliesFor one person, it is. A team needs more: several sources in a priority order, shadowed conflicts reported instead of guessed, a preflight before anything is linked, and a sync that refuses to overwrite a folder it did not make.

“Why not a git submodule?”

We could vendor the team repository as a submodule straight into the skills folder.

A reader who likes submodules, mostly

The editor repliesThen the agent folder becomes the database, and local experiments live inside someone else's checkout. Dalo keeps checkouts in its store, links only the resolved result, and blocks a refresh when a team checkout is dirty rather than lose your edit.

“We just paste them into chat.”

When someone writes a good skill, they share it in the team channel. People copy what they need.

A reader with a busy team channel

The editor repliesThat is how versions drift. With Dalo a skill has one home in Git, one approved version, and every machine resolves it the same way.

Recovery

Corrections & clarifications

A reader typed a command with a transposed letter. Dalo printed this correction:

dalo synkerror: unrecognized subcommand 'synk'  tip: a similar subcommand exists: 'sync'

A skill name was misspelled in an approval. The record now reads:

dalo approve skill company:relese-helpererror: skill `company:relese-helper` was not found; did you mean `company:release-helper`?; known skills: company:new-skill, company:release-helper

Every blocking state names the next command. For everything else, dalo doctor turns health into findings, each with a fix.

A6  ·  Also in this edition

Public catalogs. Select only the skills you want from a public catalog. Each selection is pinned, and none reaches an agent before you approve it.

Team manifests. A team repository's dalo.toml composes commit-pinned catalogs with dalo team catalog add. +copywriting includes a skill, -seo-audit excludes one, and skills = [] selects all.

Instruction packs. Shared conventions are rendered into managed blocks inside agent instruction files. Everything outside those markers stays yours.

Autosync. A launchd job or systemd user timer keeps agent folders current. Scheduled runs apply existing approvals and never grant new ones.

Portable plugins. PLUGIN.toml can declare tools and hooks. Each is approved separately, by the SHA-256 of its exact contract; change one field and the approval is gone.

Adopt. An agent wrote a useful skill straight into its own folder? dalo adopt brings it under management without losing the original.
