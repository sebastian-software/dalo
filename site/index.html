Your team's agent skills, versioned like code.

For engineers and team leads who run Claude Code, Codex, or another agent across several people and machines: keep every skill in Git, resolve one approved set, and link it into the folders your agents already read.

curl -fsSL https://dalo.sh/install.sh | sh

Six release targets, each published with a SHA-256 checksum and Sigstore provenance — and no skill reaches an agent folder before a security audit and your explicit approval.

Agent skills are becoming operational knowledge.

They encode how your team works. But most of them still live in one machine's folder, a pasted snippet, or a chat thread. Over time, versions diverge, ownership blurs, and the same skill behaves differently for everyone.

The usual flow

  • install this skill here
  • copy that folder there
  • pick the target agent again
  • hope nobody changed the public repo
  • hope the local edit doesn't get lost
  • hope the team runs the same version

With Dalo

  • every skill versioned in Git
  • resolved deterministically
  • synced across the whole team
  • private work kept separate
  • existing files never touched
  • ready to promote when it proves out

What Dalo gives you.

01

One source of truth

All skills live in Git, locally and across the team. Dalo's store becomes the single, versioned source of truth, so the team repository stays a clean input and your agent folders stay an output.

~/.dalo/
  • local/ private skills, git-tracked
  • sources/ team checkouts
  • lock.toml resolved set
02

Deterministic resolution

The resolver is a pure function: given your sources and config, it returns the same result every time. Source priority decides conflicts, lower wins. Re-running on the same inputs is byte-for-byte identical.

localprio 0wins
companyprio 10shadowed
ossprio 20shadowed

same name review · one slot · highest priority linked

03

Safe sync

Dalo only writes paths it owns. It links resolved skills as directory symlinks, removes only the links it created, and never overwrites a real file or folder it didn't make. --dry-run prints the plan and writes nothing.

unmanaged files left untouched
only Dalo-owned symlinks removed
conflicts reported, never forced
04

Review before delivery

A local preflight runs 15 deterministic rules over every active skill before a link is created. High and critical findings block the sync until someone records an explicit, content-bound exception. Catalog skills stay pending until you run dalo approve skill, and an optional sandboxed agent reviewer can add findings but never clears one.

15 deterministic rules, run locally
high or critical findings block
approvals are source-qualified
agent review adds, never approves
05

Team-composed catalogs

A team repository can combine its own skills with external skill sets. Use dalo team catalog add to pin an immutable Git commit in dalo.toml, then apply explicit filters: + includes a skill and - excludes it. An empty list selects all.

team catalog manifest
  • version one immutable upstream commit
  • +copywriting include explicitly
  • -seo-audit exclude explicitly
  • skills = [] select everything
06

Plugins with tools and hooks

A portable package ships more than text: PLUGIN.toml can declare executable tools and the hooks that call them on agent events. Dalo approves every tool and every hook separately, by the SHA-256 hash of its exact contract, and projects the approved set into the Codex and Claude package layouts. Change one field and the approval is gone.

PLUGIN.toml
  • [[tool]] staged, never run to approve
  • [[hook]] needs its tool approved first
  • @sha256:… the exact contract, hashed
  • approval re-verified before every run

  • Managed instruction packs

    Shared conventions live as versioned Markdown. Dalo renders them into explicit managed blocks, preserves everything outside those markers, and warns when active packs declare overlapping topics.

    dalo instructions list

  • Scheduled autosync

    A background job keeps agent folders current hourly, daily, or weekly through launchd, a systemd user timer, or cron. Scheduled runs stay fail-closed: they apply existing approvals and never grant new ones.

    dalo autosync install

How it works

Dalo is a small pipeline: it turns many skill sources into one reviewed set, then links that set into the folders your agents already read. Nothing passes the review stage without a clean audit and your approval.

Sources Local + team your machine and Git repos
Store ~/.dalo normalized, versioned
Review Preflight audit & approval gate
Resolver Deterministic priority & conflict rules
Targets ~/.agents/skills ~/.claude/skills ~/.hermes/skills

The agent folder is an output, not the database. That one boundary keeps team repos clean, local experiments private, and existing files safe to inspect.

From local experiment to team standard.

A path that scales from a single developer to the whole org, one step at a time.

  1. 1

    Adopt

    An agent wrote a useful skill straight into its own folder. Bring it under management without losing the original. Dalo copies it into your local source first.

    dalo adopt release-notes.local
  2. 2

    Add a source

    Connect a team repository of shared skills. Its checked-in dalo.toml can also compose commit-pinned external catalogs, so every teammate resolves the same declared selection.

    dalo source add company git@github.com:acme/agent-skills.git
  3. 3

    Review and approve

    Read the evidence with dalo audit company:release-helper before anything reaches an agent folder, then record the decision. Approvals are source-qualified and stay in your own store.

    dalo approve skill company:release-helper
  4. 4

    Sync

    Resolve every active source into one set and link it into your agent folders. Safe to run any time; dirty edits block instead of getting lost.

    dalo sync

Up and running in minutes.

Install with Homebrew, the hosted script, npx getdalo, Cargo Binstall, Cargo, or a prebuilt archive from GitHub Releases. Dalo shells out to git for source operations; there is no daemon.

curl -fsSL https://dalo.sh/install.sh | sh

Prefer Node? Run npx getdalo --version or npm install --global getdalo. Prefer Rust tooling? crates.io supports cargo binstall dalo and cargo install dalo.

On Windows? Dalo runs under WSL; use the standalone command from your WSL shell.

Installing through an AI agent? Point it to dalo.sh/install.md.

Safe by design.

Dalo is conservative on purpose. It protects the work that's already on your disk, and it makes every change visible before and after it happens.

Protects unmanaged files

If a real skill folder already holds a slot, Dalo reports the conflict and leaves it exactly where it is. It never overwrites what it didn't create.

Trust is explicit

Adding a source is the trust decision: a repository you add with dalo source add is trusted, and its skills still run through the preflight on every sync. A catalog is the opposite — each skill stays an offer until you select it and approve it with dalo approve skill source:skill. Approvals are source-qualified and live in your own store; scheduled runs apply existing decisions but never make new ones.

Security preflight and review gate

Every active skill is checked before sync against 15 deterministic rules, and nothing it cannot read passes silently. High or critical findings block links until an explicit, content-bound risk acceptance covers them. dalo audit shows the evidence, and an optional sandboxed agent reviewer can add findings but never clears one. Read the security overview for every guarantee and its limits.

Executables are approved by hash

A plugin's tools and hooks are approved one at a time, by the SHA-256 hash of the exact contract — entry, arguments, environment, staged files, and for a hook the tool it calls. Dalo re-checks that approval before it dispatches a handler, so revoking one disables an already-installed sidecar.

Visible conflicts

Same-name skills resolve by priority and the rest are reported as shadowed, not silently dropped. status explains every state.

Dirty work blocks, not breaks

Edited a team skill in place? The source is dirty, and sync stops for it instead of discarding your change. The default is no data loss.

Dry-run everything

The same planning path drives real runs and --dry-run. See exactly which symlinks would be created or removed before anything changes.

Built-in diagnostics

dalo doctor checks store structure, lockfiles, Git availability, target paths, and broken symlinks, so you can trust the result.

None of this makes a third-party skill safe. It makes the decision to run one explicit, reviewable, and reproducible — and the limits are written down too.

Helpful by default

Get it wrong. Dalo gets you back.

Mistype a command and Dalo suggests the right one. Reference a skill that does not exist and it lists the ones that do. When sync blocks, the output is the fix: the exact command to run next.

dalo doctor turns a broken state into a runnable to-do list, so getting unstuck does not mean searching docs or reconstructing state.

Why not just install skills directly?

Single-user installers are useful for trying a skill. Dalo starts where that flow gets awkward for teams: review, provenance, version drift, and safe rollout across several agent folders.

One-off installer

Good for one machine.

Weak once a team needs review, shared versions, and the same result on every laptop.

Dotfile repo

Too broad for agent skills.

Great for personal setup, risky when skill rollout can overwrite unrelated environment files.

Git submodule

Pins a repo, not a selection.

Useful for one external source, awkward for catalogs where you only want three skills out of forty.

Copy-paste

Fast until nobody knows what changed.

No drift detection, no provenance, and no clean path from local experiment to team standard.

Built to rely on.

Dalo is v0.15.1, and everything a team workflow rests on ships today: local, team, and catalog sources; deterministic resolution; security audits and review gates; safe sync; adoption; diagnostics; and instruction packs. These are the commitments the 1.x line is written to keep.

The surface you script against holds

Commands, flags, exit codes, --json shapes, environment variables, and every file Dalo persists are tier 1: additive inside 1.x, breaking only in a major, each deprecation announced a minor ahead and never silently.

Read the 1.x compatibility contract

Your store upgrades itself

A store written by 0.6.0 or later opens with no migration command, no re-approval, and nothing unlinked. That is a test, not a claim: the suite replays stores written by the released 0.6.0, 0.9.2, 0.12.0, and 0.15.1 binaries.

Signed builds, six ways to install

Every release publishes archives for six targets — macOS and Linux, x86_64 and aarch64, gnu and musl — each with a SHA-256 checksum and a Sigstore bundle. Six install channels keep publishing every 1.x release; retiring one is a breaking change.
